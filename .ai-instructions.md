## 2. Engineering Standards

> [!IMPORTANT]
> These standards apply to **every code change**. They are the quality bar, not aspirational guidelines. Agents must internalize these before writing code.

### Quality Gates

| Gate             | Directive                                                                                                                                                                                                       |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Correct**      | Tests prove functional behavior. Correctness is the floor, not the finish line — never treat a passing test as proof of quality.                                                                                |
| **Elegant**      | Every abstraction must earn its cost. If you add a layer, state what it buys and what it costs (CPU, memory, complexity).                                                                                       |
| **Efficient**    | Every line has mass. No redundant parsing, no gratuitous buffer copies, no allocations inside hot loops. Prefer direct data transfer over serialization acrobatics (no base64-over-JSON when a socket will do). |
| **Maintainable** | A future reader must understand intent without decoding execution. Structure > comments. If logic can only be safely changed by whoever wrote it, refactor it.                                                  |
| **Responsive**   | Latency is a bug. Startup time matters. Idle CPU is suspicious. Software should feel immediate.                                                                                                                 |

### Operational Disciplines

| Discipline                 | Directive                                                                                                                                                                                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Hot Paths**              | Identify and protect performance-critical paths. These deserve manual attention — not assumption, not AI boilerplate.                                                                                                                                  |
| **Profiling & Regression** | Performance is a build artifact. Track startup time, steady-state memory, key transaction latency. Recommend measurement before and after non-trivial changes.                                                                                         |
| **Dependencies**           | A dependency is a liability until proven useful. Before adding any package: state what it buys *the user* (not the developer schedule), and what it costs (RAM, startup time, security surface, update churn).                                         |
| **Resource Budgets**       | Treat memory, CPU, startup time, and network as scarce. This machine runs a 24B model that nearly fills 12 GB VRAM — there is no slack. Every MB and every wakeup matters. Resource budgets are grounded in the hardware constraints documented in §4. |

### AI-Specific Guardrail

> [!CAUTION]
> AI reflects median training patterns. Median code is plausible, verbose, layered, and defensively over-abstracted. Before committing AI-generated code:
>
> - Verify it doesn't add unnecessary abstraction layers
> - Check for serialization overhead (the base64-over-JSON anti-pattern)
> - Confirm dependencies are justified, not just convenient
> - Look for the "thousand small sloppiness decisions" that compound invisibly

## 3. Coding Conventions

### Python Docstrings

- **Requirement:** Every script and major function MUST have a Google-style docstring.
- **Goal:** Enable the AI to understand the script's purpose via tool inspection without reading the full source.
- **Reference:** See the guide in the brain artifact for detailed examples.

### Markdown Instructions

- **Requirement:** Use GitHub-style Alerts (`> [!IMPORTANT]`, `> [!NOTE]`) for mission-critical instructions within `.md` files.

### Workspace Folder Hygiene & Separation

- **Data Directory (`data/`)**: Contains all persistent application states, databases (`evelyn_chat.db`, `evelyn_memory.db`), ChromaDB vectors, and sync state JSONs. Keep this directory isolated from code.
- **Scripts Directory (`scripts/`)**: Reserved for standalone utilities, one-off processors, and maintenance tools (e.g., `update_frontmatter.py`, `migrate_context_to_sqlite.py`).
- **Root `scratch/` Directory (`scratch/`)**: Reserved for temporary, one-time, or limited-use scripts, database search utilities, diagnostics, and diagnostic outputs.
  - Active diagnostic scripts (e.g., `db_search.py`, `db_thinking_audit.py`) reside in the root `scratch/` folder.
  - Stale experimental scripts, old trace tools, or diagnostic output logs must be archived into organized subdirectories to keep the root folder clean and tidy.
- **Evelyn `tools/` Directory (`Evelyn/tools`)**: Reserved strictly for permanent system-level scripts, ingestion pipelines, core tools, database utilities, and active runtime modules used consistently in daily operations (e.g., `fact_extractor.py`, `pending_reviewer.py`, `undo_thread.py`). Never store scratch files, test scripts, or one-off log files here.

### File Metadata & Frontmatter

- **Requirement:** Whenever you create or modify a `.md`, `.txt`, `.py`, or `.ps1` file, you MUST manually execute `python scripts/update_frontmatter.py "<absolute_path>"` via the terminal on that file afterwards to keep the creation/modification timestamps and metadata headers accurate.
- **Why:** The user relies on VS Code's "Run on Save" to handle this, but AI tool edits bypass that trigger. It is your responsibility to execute the script after edits.

### Foam / Obsidian Knowledge Graph Integrity

- **Requirement:** When linking files together inside `.py` and `.ps1` scripts using `[[WikiLink]]` syntax, you **must not** indent the link comments by 4 or more spaces.
- **Why:** Foam parses `.py` and `.ps1` notes using a standard Markdown parser. In Markdown specification, any line indented by 4 or more spaces is treated as an *indented code block*, which disables all hyperlink and wikilink parsing. Indented links are completely invisible to Foam's search index and graph visualizer.
- **Guideline: The Hybrid Linking Strategy**
  - **Rule A (Global Header Registry)**: List overarching module dependencies and design specifications in the zero-indentation block at the top of the file:

    ```python
    # references: [[System_Directives]], [[ROADMAP.md]]
    ```

  - **Rule B (Left-Margin Contextual Comments)**: Keep functional context adjacent to its implementation by placing left-margin comments (zero indentation) right above the target function:

    ```python
    # Implements memory refresh protocol: [[start-services.md]]
    def trigger_system_refresh():
        # Code is indented inside, but link above has 0 leading spaces!
        run_refresh_logic()
    ```

  - **Let VS Code Handle Code-to-Code**: Do not write wikilinks for standard Python script-to-script navigation. Use VS Code's native `F12` / `Ctrl+Click` (Pylance language server) for navigating class and function definitions. Limit Foam wikilinks in code to **Code-to-Concept** bridges (linking scripts to `.md` roadmaps, requirements, guidelines, or persona instructions).

## 5. Workflow & Operations

- **Service Startup:** If services (Ollama, Evelyn server, ComfyUI, etc.) are down, refer to `.agents/workflows/start-services.md`.
- **Quality Review:** After completing significant features or refactors, run `/quality-review` for a structured self-review against §2 standards.
- **Avoid Redundant Searches:** If a path is listed in §1 or in `reference/engine_architecture.md#4-related-workspace-paths--integrations`, use it directly rather than using `find_by_name`.
- **No Open WebUI dependency**: Evelyn is fully custom. Any reference to Open WebUI in code or comments is stale and should be removed.

> [!CAUTION]
> **NEVER run commands as background tasks in this workspace.**
>
> The user works in VS Code's integrated terminal. Background tasks (`WaitMsBeforeAsync` set low, or any async dispatch) cannot be monitored, cannot be brought to the foreground, and produce output the user cannot see or interact with.
>
> **Rules:**
>
> - Always run `python evelyn_server.py` and similar long-running processes **synchronously** (high `WaitMsBeforeAsync`, or instruct the user to run it themselves in their terminal).
> - If a command needs to run in the foreground so the user can monitor it, say so explicitly and let the user execute it.
> - **Never** use background dispatch as a shortcut to avoid waiting. The user's ability to observe and control running processes is more important than agent convenience.
