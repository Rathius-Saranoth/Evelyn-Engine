## Evelyn Project: AI Instructions

This file is the **binding operational contract** for AI Agents (Antigravity, Cursor, Copilot) working within the `LocalAI` workspace. Every section is mandatory. Ignorance of a section is not a defence for violating it.

---

## 0. Operation Protocol — Mandatory Execution Order

> [!CAUTION]
> This section defines the **exact sequence** you must follow for every task. Do NOT skip steps. Do NOT reorder steps. Do NOT claim a step is complete until you have **verified it with your own tools** (file reads, grep, terminal output). "I believe I did this" is not verification — only tool output is.

### Phase A — Orient (before writing any code)

1. **Read `ROADMAP.md`** to understand current project state and what has already been built.
2. **Read `reference/engine_architecture.md`** to understand the system's structural blueprint and script relationships.
3. **Read `reference/endpoints.md`** if the task involves any API work.
4. **Read the specific files you intend to modify** — in full, or at minimum the sections you will touch. Do NOT assume file contents from memory or training data. The codebase changes frequently.

### Phase B — Plan & Confirm (HARD STOP — do not write code yet)

> [!CAUTION]
> You MUST complete this phase and receive user approval before writing any code. If the user asked a question, answer it — do not start editing files. This phase exists because models have repeatedly jumped straight to code without confirming they understood the request.

5. **Present a plan** to the user. Include:
   - What you will change (specific files and functions)
   - What you will NOT change
   - Risks or trade-offs you foresee
6. **Present a Deliverables Checklist** — a numbered list of every concrete change the user's request requires. Each item must be a verifiable, binary outcome (done or not done). This checklist becomes the contract for the rest of the task.

   Example format:
   ```
   Deliverables Checklist:
   1. [ ] Add `POST /foo` endpoint to `evelyn_server.py`
   2. [ ] Wire endpoint into `evelyn_tools.py` tool schema
   3. [ ] Update `reference/endpoints.md` with new route
   4. [ ] Test endpoint returns 200 with expected payload
   ```

7. **STOP and wait for user approval.** Do not proceed to Phase C until the user confirms the plan. If the user modifies the checklist, adopt their version as the binding contract.

### Phase C — Execute (write code)

8. **Make changes** in the smallest, most targeted edits possible. Prefer surgical replacements over wholesale file rewrites.
9. **Run `python scripts/update_frontmatter.py "<absolute_path>"`** on every `.md`, `.txt`, `.py`, or `.ps1` file you create or modify. This is your responsibility — VS Code's "Run on Save" does not trigger for AI tool edits.

### Phase D — Verify (prove correctness before claiming done)

10. **Re-read every file you modified** using your file-reading tools. Confirm the edit landed correctly. Check for:
    - Syntax errors or malformed structures
    - Unintended deletions of existing code or comments
    - Duplicate content from botched replacements
11. **Test if applicable.** Run the code, hit the endpoint, or execute the script. Read the output with your tools. If you cannot test, say so explicitly.
12. **Purge Test Artifacts & Data Hygiene.** Immediately remove any temporary test entries, dummy database rows, test proposals, or test files created in SQLite databases (`evelyn_memory.db`, `evelyn_chat.db`) or the filesystem once testing/verification is complete. Test entries must never be left behind in production databases.
13. **Walk the Deliverables Checklist from Phase B, item by item.** For each item, confirm it is satisfied with tool evidence (file read, grep, command output). Mark items complete. If any item is NOT satisfied, return to Phase C and fix it before proceeding.

> [!IMPORTANT]
> **Checkpoint rule:** If at any point during Phase D you discover your edit broke something or didn't satisfy a checklist item, you MUST fix it before proceeding to Phase E. Do NOT document incomplete work.

### Phase E — Document (update all reference materials)

13. **Update `ROADMAP.md`** if you completed a milestone or feature.
14. **Update `reference/engine_architecture.md`** (including the Mermaid diagram) if you created, renamed, deleted, or restructured any script, database, or service.
15. **Update `reference/endpoints.md`** if you added, removed, or changed any FastAPI endpoint signature, payload, or behavior.
16. **Update `requirements.txt`** if you added or changed a Python package dependency.
17. **Update `REQUIREMENTS.md`** if you added or changed a system-level dependency, external service, or environment variable.
18. **Run `python scripts/update_frontmatter.py`** on every reference document you updated in this phase.

### Phase F — Report

19. **Summarize what you did** with specifics: files changed, lines affected, tests run. Do NOT use vague language like "updated the necessary files" — name them.
20. **Print the final Deliverables Checklist** with all items marked complete. If any item was descoped or deferred, state why explicitly.

## 2. Engineering Standards

> [!IMPORTANT]
> These standards apply to **every code change**. They are the quality bar, not aspirational guidelines. Agents must internalize these before writing code.

### Quality Gates

| Gate             | Directive                                                                                                                                                                                                       |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Correct**      | Tests prove functional behavior. Correctness is the floor, not the finish line — never treat a passing test as proof of quality.                                                                                |
| **Elegant**      | Every abstraction must earn its cost. If you add a layer, state what it buys and what it costs (CPU, memory, complexity).                                                                                       |
| **Efficient**    | Every line has mass. No redundant parsing, no gratuitous buffer copies, no allocations inside hot loops. Prefer direct data transfer over serialization acrobatics (no base64-over-JSON when a socket will do). |
| **Maintainable** | A future reader must understand intent without decoding execution. Structure > comments. If logic can only be safely changed by whoever wrote it, refactor it.                                                  |
| **Responsive**   | Latency is a bug. Startup time matters. Idle CPU is suspicious. Software should feel immediate.                                                                                                                 |

### Operational Disciplines

| Discipline                 | Directive                                                                                                                                                                                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Hot Paths**              | Identify and protect performance-critical paths. These deserve manual attention — not assumption, not AI boilerplate.                                                                                                                                  |
| **Profiling & Regression** | Performance is a build artifact. Track startup time, steady-state memory, key transaction latency. Recommend measurement before and after non-trivial changes.                                                                                         |
| **Dependencies**           | A dependency is a liability until proven useful. Before adding any package: state what it buys *the user* (not the developer schedule), and what it costs (RAM, startup time, security surface, update churn).                                         |
| **Resource Budgets**       | Treat memory, CPU, startup time, and network as scarce. This machine runs a 12B model with a 32K context window that nearly fills the 12 GB VRAM — there is no slack. Every MB and every wakeup matters. Resource budgets are grounded in the hardware constraints documented in §4. |
| **Data Hygiene**           | Test data must never pollute persistent databases or filesystem artifacts. Always delete temporary test entries, test proposals, or dummy records immediately after verification is complete.                                                  |

### AI-Specific Guardrail

> [!CAUTION]
> AI reflects median training patterns. Median code is plausible, verbose, layered, and defensively over-abstracted. Before committing AI-generated code:
>
> - Verify it doesn't add unnecessary abstraction layers
> - Check for serialization overhead (the base64-over-JSON anti-pattern)
> - Confirm dependencies are justified, not just convenient
> - Look for the "thousand small sloppiness decisions" that compound invisibly

**Source:** `reference/Notes to Live By (Tech Version).md` — see the full document for context and rationale.

## 3. Coding Conventions

### Python Docstrings

> [!IMPORTANT]
> **Google-style is the sole docstring standard.** Sphinx-style (`:param:`) and NumPy-style are not used.
> Every module and every non-trivial function MUST have a docstring. Missing docstrings are a defect.

#### The Two Documentation Populations

This codebase has two distinct documentation targets. Do NOT confuse them:

| Population | Who Reads It | Location | Format |
|---|---|---|---|
| **LLM Tool Dispatch** | Gemma 4 (Ollama) at runtime | `"description"` fields in `MODEL_TOOL_DEFINITIONS` JSON in `evelyn_tools.py` | Free-form imperative prose |
| **Code-Agent Navigation** | AI agents + human devs | Python docstrings across all files | Google-style |

> [!CAUTION]
> The Python function docstrings on tool functions (e.g. `write_journal_entry`, `search_vault`) are **never read by Ollama**. Ollama reads only the `"description"` strings inside `MODEL_TOOL_DEFINITIONS`. Editing a Python docstring has NO effect on model tool behavior.

**`MODEL_TOOL_DEFINITIONS` description format (imperative prose):**
- Lead with `"Use when..."` and `"Do NOT use for..."`  
- Include tool-selection ordering: `"Prefer X over Y when Z"`
- Never duplicate the JSON schema's type information — explain *when* and *why*, not *what*

#### Google-Style Docstring Tiers

Apply docstrings at the right level of detail for each context:

**Tier 1 — Module docstrings** (navigation aid, max 15 lines):
```python
"""
module_name.py — One-line purpose statement.

Exports:
  primary_function()   — What it does, one line.
  secondary_function() — What it does, one line.

Key config: evelyn_config.py (RELEVANT_CONSTANTS)
See also: reference/engine_architecture.md
"""
```

**Tier 2 — Simple function docstrings** (≤1 meaningful param, obvious return) — one-liner only:
```python
def clear_history():
    """Delete all messages from the chat history database."""
```

**Tier 3 — Non-trivial function docstrings** (≥2 params OR non-obvious return/side-effects):
```python
def some_function(param_a: str, param_b: int = 5) -> dict:
    """One-line summary of what the function does.

    Optional 1-2 sentences on WHY a design decision was made or a
    non-obvious behavior. Omit if the signature is self-evident.

    Args:
        param_a: Description. Include constraints or valid values if non-obvious.
        param_b: Description. State the default and what it controls.

    Returns:
        What is returned and in what form. Include "Empty list if..." or
        "None on failure" where applicable.

    Raises:
        ValueError: Only document exceptions the caller needs to handle.
    """
```

#### Verbosity Rule

> [!NOTE]
> Document *why* a parameter has a non-obvious value, or *why* a behavior was intentionally omitted.
> Do NOT document what is already visible in the signature or a 5-second code read.
> If a module docstring exceeds 15 lines, its content belongs in `reference/` — not in a docstring.

#### Enforcement Checklist (apply on every file you touch)

- [ ] Module has a docstring (Tier 1 format, ≤15 lines)
- [ ] Every function with ≥2 params uses Google-style `Args:` / `Returns:`
- [ ] No function is missing a docstring entirely
- [ ] No docstring uses Sphinx-style (`:param:`, `:return:`)
- [ ] `MODEL_TOOL_DEFINITIONS` descriptions were NOT modified to fix a docstring issue (wrong target)

### Markdown Instructions

- **Requirement:** Use GitHub-style Alerts (`> [!IMPORTANT]`, `> [!NOTE]`) for mission-critical instructions within `.md` files.

### Workspace Folder Hygiene & Separation

- **Data Directory (`data/`)**: Contains all persistent application states, databases (`evelyn_chat.db`, `evelyn_memory.db`), ChromaDB vectors, and sync state JSONs. Keep this directory isolated from code.
- **Project Scripts Directory (`scripts/`)**: Reserved for standalone utilities, one-off processors, and maintenance tools (e.g., `update_frontmatter.py`, `migrate_context_to_sqlite.py`).
- **Root `scratch/` Directory (`scratch/`)**: Reserved for temporary, one-time, or limited-use scripts, database search utilities, diagnostics, and diagnostic outputs.
  - Active diagnostic scripts (e.g., `db_search.py`, `db_thinking_audit.py`) reside in the root `scratch/` folder.
  - Stale experimental scripts, old trace tools, or diagnostic output logs must be archived into organized subdirectories to keep the root folder clean and tidy.
- **Evelyn `tools/` Directory (`Evelyn/tools`)**: Reserved strictly for permanent system-level scripts, ingestion pipelines, core tools, database utilities, and active runtime modules used consistently in daily operations (e.g., `fact_extractor.py`, `pending_reviewer.py`, `undo_thread.py`). Never store scratch files, test scripts, or one-off log files here.

### File Metadata & Frontmatter

- **Requirement:** Whenever you create or modify a `.md`, `.txt`, `.py`, or `.ps1` file, you MUST manually execute `python scripts/update_frontmatter.py "<absolute_path>"` via the terminal on that file afterwards to keep the creation/modification timestamps and metadata headers accurate.
- **Why:** The user relies on VS Code's "Run on Save" (configured via the background extension `emeraldwalk.runonsave`) to handle this. However, direct filesystem writes from AI agent tools bypass the editor's save hooks, so it is your responsibility to execute the script manually after editing.

### Foam / Obsidian Knowledge Graph Integrity

- **Requirement:** When linking files together inside `.py` and `.ps1` scripts using `[[WikiLink]]` syntax, you **must not** indent the link comments by 4 or more spaces.
- **Why:** Foam parses `.py` and `.ps1` notes using a standard Markdown parser. In Markdown specification, any line indented by 4 or more spaces is treated as an *indented code block*, which disables all hyperlink and wikilink parsing. Indented links are completely invisible to Foam's search index and graph visualizer.
- **Guideline: The Hybrid Linking Strategy**
  - **Rule A (Global Header Registry)**: List overarching module dependencies and design specifications in the zero-indentation block at the top of the file:

    ```python
    # references: [[System_Directives]], [[ROADMAP.md]]
    ```

  - **Rule B (Left-Margin Contextual Comments)**: Keep functional context adjacent to its implementation by placing left-margin comments (zero indentation) right above the target function:

    ```python
    # Implements memory refresh protocol: [[start-services.md]]
    def trigger_system_refresh():
        # Code is indented inside, but link above has 0 leading spaces!
        run_refresh_logic()
    ```

  - **Let VS Code Handle Code-to-Code**: Do not write wikilinks for standard Python script-to-script navigation. Use VS Code's native `F12` / `Ctrl+Click` (Pylance language server) for navigating class and function definitions. Limit Foam wikilinks in code to **Code-to-Concept** bridges (linking scripts to `.md` roadmaps, requirements, guidelines, or persona instructions).

- **Cross-File Anchor Rule:** Do **not** use `[[file#anchor]]` syntax for cross-file WikiLinks. Foam's anchor slug generator is unreliable — it handles special characters (`&`, `/`, `.`, `(`, `)`) inconsistently and does not match GitHub's slug algorithm. This causes persistent "Cannot find section" IDE warnings that cannot be suppressed via config.
  - ✅ `[[endpoints.md]] §5 (memory triaging)` — link to the file, use §-notation for section context
  - ❌ `[[endpoints.md#5-developer-and-review-queue-apis]]` — cross-file anchor; Foam will fail to resolve it
  - **Rule:** Link to the file only. If section context matters, add a `§N` reference inline after the link.

## 5. Workflow & Operations

- **Service Startup:** If services (Ollama, Evelyn server, TTS server, Image server, etc.) are down, refer to `.agents/workflows/start-services.md`.
- **Process & Service Verification:** When checking whether a service is running (Evelyn server, TTS server, Image server, Ollama, etc.), ALWAYS inspect by **TCP Port Binding** (e.g. `Get-NetTCPConnection -LocalPort <port>` / `netstat -ano | findstr :<port>` on Windows, or `ss -tulpn` / `lsof -i:<port>` on Linux) or explicit script command line matching first. NEVER rely on generic process name searches (`python.exe`) or stale PID context from prior chat history, as this leads to false negatives on restarted processes.
- **Quality Review:** After completing significant features or refactors, run `/quality-review` for a structured self-review against §2 standards.
- **Avoid Redundant Searches:** If a path is listed in §1 or in `reference/engine_architecture.md#4-related-workspace-paths--integrations`, use it directly rather than using `find_by_name`.
- **No Open WebUI dependency**: Evelyn is fully custom. Any reference to Open WebUI in code or comments is stale and should be removed.

> [!CAUTION]
> **NEVER run commands as background tasks in this workspace.**
>
> The user works in VS Code's integrated terminal. Background tasks (`WaitMsBeforeAsync` set low, or any async dispatch) cannot be monitored, cannot be brought to the foreground, and produce output the user cannot see or interact with.
>
> **Rules:**
>
> - Always run `python evelyn_server.py` and similar long-running processes **synchronously** (high `WaitMsBeforeAsync`, or instruct the user to run it themselves in their terminal).
> - If a command needs to run in the foreground so the user can monitor it, say so explicitly and let the user execute it.
> - **Never** use background dispatch as a shortcut to avoid waiting. The user's ability to observe and control running processes is more important than agent convenience.

## 7. Anti-Hallucination Directives

> [!CAUTION]
> The following failure modes have been observed in production AI agent sessions. These rules exist because models have violated them.

| Failure Mode | Rule |
|---|---|
| **Jumping straight to code** | Phase B (Plan & Confirm) is a HARD STOP. If you start writing code before presenting a plan and receiving user approval, you have violated the protocol. Answer questions first. Plan first. Code second. |
| **Skipping the Deliverables Checklist** | Every task requires a checklist in Phase B. "I'll just make this quick change" is not an exemption. The checklist is what you verify against in Phase D. No checklist means no verification contract. |
| **Claiming work is done without verification** | You MUST re-read modified files with your tools after editing. "I updated the file" without a subsequent `view_file` or `grep_search` confirming the edit is a protocol violation. |
| **Hallucinating file contents** | Do NOT assume you know what a file contains. Read it. The codebase is modified by multiple agents and the user — your training data is stale by definition. |
| **Skipping documentation updates** | Phase E is not optional. If you changed code, check whether `ROADMAP.md`, `engine_architecture.md`, or `endpoints.md` need updates. If they don't, state why. |
| **Reporting phantom test results** | If you did not run a test or script with your `run_command` tool and read the output, do NOT claim it passed. Say "I did not test this" instead. |
| **Vague completion summaries** | "Updated the necessary files" is banned. Name every file. State what changed in each. |
| **Skipping frontmatter updates** | `python scripts/update_frontmatter.py` must run on every file you touch. This is Phase C, step 9. Not optional. |
| **Inventing endpoints or functions** | Before calling a function or hitting an endpoint, verify it exists in the codebase. Do not invent API routes from the ROADMAP description alone. |
